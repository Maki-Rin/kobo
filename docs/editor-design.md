# スタッフ用投稿画面 設計メモ

更新: 2026-10-26 / 状態: 方針決定、未着手

KOBOスタッフ（非エンジニア、最大20人程度）が、開発者なしで記事・作品・イベントを編集・公開できる仕組み。既製CMSは導入せず、Next.js内に自作する。

## 方針

- 特定サービスに依存しない。Vercel、Gitホスティング、DBはいつでも差し替えられる構成にする。
- コンテンツの正本は今のまま Git 上のファイル（`src/content/articles/*.md`、`public/data/*.json`、画像）。
- 投稿画面は差し替え可能な「入口」にすぎず、なくなってもコンテンツは残る。
- 誰が何を変えたかを必ず記録する（事故・トラブル防止）。
- 公開は自動。開発者のレビューを待たず、自動チェックと「いつでも戻せる」ことで安全を担保する。

## 検討して見送ったもの

| 候補 | 見送り理由 |
|---|---|
| EmDash | Astro製でサイト全面作り直し。2026-04公開の開発者プレビュー段階 |
| microCMS | 利用規約第7条で認証情報の第三者利用を禁止（共通アカウント不可）。個人アカウント20人だと Team プランで月約25,000円。権限管理はBusiness以上 |
| Keystatic / Decap 等のGitベースCMS | 編集者全員にGitHub等のアカウントが必要 |
| Payload CMS | OSSで個人アカウント無制限だが、コンテンツがDBとPayloadのスキーマに依存する |

## 構成

```
スタッフ ──(パスキーでログイン)──> /admin（Next.js内）
                                   │ 入力・画像・プレビュー
                                   ▼
                        自動チェック（不合格なら理由を表示して止める）
                                   │
                                   ▼
                  Bot が main へコミット（編集者名を記録）
                                   │
                                   ▼
                       ホスティング先が自動ビルド → 公開
```

## ログインと権限

- 個人ごとのパスキー（WebAuthn）。パスワードとメール送信サービスは使わない。
- 招待制。まとめ役が招待リンクを発行し、受け取った人が端末で登録する。
- 端末紛失・機種変更時は、まとめ役が再招待する。退任者はまとめ役が無効化する。
- ロール:
  - 編集者: 記事・作品・イベントの作成・編集・非公開化。自分の変更を戻す。
  - まとめ役: 編集者の権限に加え、アカウント招待・無効化、他人の変更を戻す。
  - 開発者: サイトのコード。投稿画面からはコードに触れない。
- 最初のまとめ役は開発者が設定する。以後はスタッフ内で引き継げるようにする。

## 編集の記録

- 保存はすべてGitコミット。コミットに編集者を記録する（例: `Co-authored-by` ではなく、コミット本文に `Editor: <表示名> <ユーザーID>`）。
- 管理画面に変更履歴（いつ・誰が・何を）を表示する。Gitを知らなくても見られる。
- ログイン・招待・無効化・戻す操作は監査ログに残す。

## 事故防止

| 仕組み | 内容 |
|---|---|
| プレビュー | 保存前に本番と同じ見た目で確認 |
| 自動チェック | ビルド成功、必須項目（タイトル・日付・著者・カバー画像）、画像サイズと形式、リンク切れ、Markdownの構文 |
| 戻す | 履歴から1クリックで前の版へ。revertコミットとして記録 |
| 削除しない | 削除は「非公開」扱い。完全削除は開発者のみ |
| 書き込み範囲の制限 | Botが書けるのはコンテンツ用ディレクトリだけ。コード・設定は対象外 |
| 同時編集 | 保存時に元の版と比較し、他人の変更を上書きしそうなら止める |

## データ

- コンテンツ: Git上のファイル（正本）。
- ユーザー・パスキー公開鍵・招待・監査ログ: 小さなDB。SQLite互換（ローカルSQLite、Cloudflare D1、Turso等）にして移行可能にする。
- 画像: 当面はリポジトリ内（`public/images/`）。容量が問題になったらオブジェクトストレージ（S3互換）へ移す。

## 依存と差し替え

| 依存先 | 差し替え方 |
|---|---|
| Gitホスティング（現在GitHub） | コミット部分を抽象化。Gitea等へ移る場合はそこだけ変更 |
| デプロイ先（現在Vercel） | Git push で自動ビルドする仕組みならどこでも可 |
| DB | SQLite互換の範囲で選ぶ |
| Botの認証情報 | サーバー側の環境変数のみ。スタッフには渡さない |

## 進め方

1. レイアウト確定
2. プリンタ稼働状況ページの公開（`feature/printer-status`、見方の説明はページ内に記載）
3. 本機能の実装。最小版（ログイン・記事の作成と編集・自動チェック・即公開・戻す）から始め、作品・イベント・画像管理・履歴画面を順に足す

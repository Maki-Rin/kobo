# 無料枠の使用量を抑える運用

2026-11-03に共有されたVercelの画面では、直近30日間のチーム全体の配信量は2.77GB / 100GB、CDNリクエストは約83,000 / 1,000,000だった。KOBO以外のプロジェクトも含む数値で、KOBO単独の使用量ではない。

## 画像

- `public/images` の75枚は、軽量化前の約151.81MiBから約27.65MiBへ削減した。
- 大きな写真は長辺2400px以内のWebP、PNGの操作画面・チラシは長辺2400px以内に縮小してから可逆圧縮のWebPに変換。人物アイコンは長辺256px以内にする。小さい既存画像は変換しない場合がある。
- 記事やコンポーネントの画像パスを更新し、従来のURLは `src/lib/image-redirects.json` とNext.jsのリダイレクトで新しい画像へ転送する。
- 投稿画面では本文画像を長辺1920px以内、人物アイコンを長辺256px以内に縮小する。小さくても解像度が過大な画像は縮小する。本文のGIFアニメーションは維持し、アイコンは静止画にする。
- 縮小では元画像以上のサイズへ拡大しない。WebPを書き出せないブラウザではPNGなどへフォールバックする。

Node.js 22で次を実行すると、今後追加した既存画像の軽量化を確認できる。

```sh
npm run images:optimize
```

実際にファイルと参照先を更新する場合:

```sh
npm run images:optimize -- --write
```

書き換える前の画像はローカルの `.editor-local/image-originals/` に退避する。このフォルダはGitに追加しない。画像の差し替えは配信・デプロイ対象の容量を減らすが、Gitの過去の履歴から元画像を消すものではない。既存のGit履歴は書き換えない。

## プリンター表示

トップページとプリンター一覧は、表示されているタブで30秒間隔の取得を継続する。非表示になるとタイマーと進行中の取得を止め、再び表示されたらすぐ取得する。通信が遅い場合は完了を待ってから次のタイマーを設定し、重複取得を防ぐ。

## 保存とデプロイ

人物の名前・紹介・アイコンは、保存ボタンでJSONと画像をまとめてGitHubへ1コミットする。Vercelはそれを受けて再デプロイする。複数人の変更をまとめてから保存すれば、細かく保存するよりデプロイ回数を抑えられる。

記事・作品・イベントの下書き保存はD1だけに保存し、本番デプロイを起こさない。公開済みの版はそのままにし、「公開する」「更新を確定」の操作で本文・画像をまとめてGitへ反映する。変更なしの保存では新しいコミットを作らない。

公開前の画像もD1へ一時保存する。元データ合計200MiBで受付を止め、未使用のまま30日経過した画像は次回アップロード時に整理する。下書きで使っている画像は維持する。Base64とDB管理領域の分、実際のD1保存容量は元データより大きくなる。適用前に `0005_drafts.sql` を本番DBへ追加する。

## 確認場所

VercelのUsageではチーム全体の配信量・CDNリクエスト・Function呼び出し・CPU・Deployment Storageを確認する。プロジェクト別に絞り込み、KOBOと他のサイトの使用量を分けて見る。画像の軽量化が、すでに記録された過去30日間の使用量を減らすことはない。
